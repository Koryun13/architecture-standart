# FURPS+: онлайн-заявки на депозиты (MVP)

Архитектурно значимые требования к MVP подачи заявок на депозит через сайт и интернет-банк. Требования, добавленные сверх полученных от бизнеса и IT-команд, помечены **[доп.]** — обоснование в колонке «Комментарий».

| Код | Требования | Комментарий |
|-----|------------|-------------|
| F   | **Функциональные (Functionality)** | |
| F1  | Сайт показывает новому клиенту список доступных депозитов и накопительных счетов с актуальными базовыми ставками. | Ставки должны браться из единого источника (см. F8), а не дублироваться на сайте вручную. |
| F2  | Новый клиент подаёт заявку на депозит на сайте, указав Ф. И. О. и номер телефона. Заявка передаётся в систему кол-центра. | Сайт не работает с АБС: заявка — это лид для кол-центра, клиента в банке ещё нет. |
| F3  | Оператор кол-центра видит заявку с сайта в системе кол-центра, звонит клиенту, рассказывает об условиях и может предложить особые условия. | Требует доработки системы кол-центра (приём лидов, карточка заявки, просмотр ставок). Систему можно расширять силами Java-специалистов команды АБС. |
| F4  | После звонка новый клиент приглашается в отделение для идентификации; заявка с сайта доступна сотруднику отделения. | Банк не может принять нового клиента без очной проверки документов. |
| F5  | В интернет-банке клиент видит список депозитов с актуальными ставками и персонализированные ставки лично для него. | Персональная ставка зависит от остатков клиента и кредитного риска — рассчитывается в АБС (F8, F9). |
| F6  | Клиент интернет-банка подаёт заявку на открытие депозита, указав счёт списания и сумму. | Проверка достаточности средств на счёте — до отправки заявки. |
| F7  | Подача заявки подтверждается одноразовым СМС-кодом. Отправка СМС реализуется силами команды банка, без доработки ядра интернет-банка у подрядчика. | Функционал СМС в ядре требует доработки подрядчиком — выносим в отдельный сервис уведомлений, работающий через существующий СМС-шлюз. |
| F8  | Ставки по депозитам ведутся в АБС (а не в XLS-файлах): ввод базовых ставок, ежедневное обновление, история изменений. С ними работают сотрудники бэк-офисов депозитов и кредитов. | Единый источник ставок для всех каналов (сайт, ИБ, кол-центр, отделения). |
| F9  | Процесс согласования ставки по заявке (в т. ч. специальной ставки для крупных клиентов) реализуется в АБС: менеджер депозитов запрашивает, сотрудник кредитования передаёт оценку кредитного риска, ставка фиксируется в заявке. | Заменяет переписку по почте; разграничение доступа — см. +R5. |
| F10 | На этапе MVP заявку из интернет-банка обрабатывает менеджер бэк-офиса: подтверждает условия депозита в АБС, после чего депозит открывается. | Целевое состояние (через год) — автоматическое открытие без бэк-офиса; архитектура MVP должна позволять его без переделки. |
| F11 | Клиент получает СМС-уведомление после подтверждения размера ставки и после открытия депозита. | Используются события изменения статуса заявки. |
| F12 | Клиент видит в интернет-банке статус своей заявки (принята, на рассмотрении, ставка подтверждена, депозит открыт, отклонена). **[доп.]** | Снижает число звонков в кол-центр от клиентов старшего возраста, которые не понимают, что происходит с заявкой. |
| F13 | Ставки доступны операторам кол-центра банка и партнёрского кол-центра. **[доп.]** | Нужны для консультаций (развивается в задании 4). |
| U   | **Удобство использования (Usability)** | |
| U1  | Интерфейсы сайта и интернет-банка соответствуют принятой в банке дизайн-системе: привычные цвета и брендированные элементы. | Требование бизнеса. Новые фронтенд-компоненты (React) переиспользуют библиотеку компонентов дизайн-системы. |
| U2  | Подача заявки занимает не более 3 шагов: выбор депозита → счёт и сумма → подтверждение СМС-кодом. **[доп.]** | «Максимально удобный» интерфейс измеряем числом шагов. |
| U3  | Интерфейс адаптирован для клиентов старшего возраста: крупный шрифт, контрастность, понятные тексты ошибок, соответствие WCAG 2.1 AA. **[доп.]** | Основная аудитория банка — люди старшего возраста; ошибки UX превращаются в нагрузку на кол-центр. |
| U4  | Сайт и интернет-банк корректно работают на мобильных устройствах (адаптивная вёрстка). **[доп.]** | Цель трансформации — привлечение молодых клиентов, которые пользуются в основном смартфонами. |
| R   | **Надёжность (Reliability)** | |
| R1  | Сервисы работают 24/7 с доступностью не ниже 99,9 % (не более ~8,8 ч простоя в год). | Требование бизнеса. Распространяется и на интернет-банк. |
| R2  | При отказе ЦОД сервисы интернет-банка остаются доступными и выдерживают требуемую нагрузку: новые сервисы развёрнуты в основном и резервном ЦОД (active-active), переключение автоматическое. | Сейчас ИБ работает в одном ЦОД на одной группе серверов — требование 99,9 % невыполнимо без изменения архитектуры. |
| R3  | Интернет-банк не работает напрямую с API и БД АБС в новом процессе: обмен заявками, статусами и ставками — асинхронный, через брокер сообщений (Kafka). | БД АБС перегружена и масштабируется только вертикально; поток онлайн-заявок может поставить под угрозу работу банка. |
| R4  | Приём заявок не зависит от доступности АБС: при недоступности АБС заявки сохраняются и доставляются после восстановления. **[доп.]** | Следствие R3: клиент не должен получать ошибку из-за регламентных работ в АБС. |
| R5  | Гарантированная доставка сообщений без потерь и дублей: at-least-once + идемпотентная обработка по ID заявки, outbox-паттерн. **[доп.]** | Иначе возможны потерянные заявки или двойное открытие депозита. |
| R6  | Целевые показатели восстановления: RPO ≤ 5 минут, RTO ≤ 15 минут для новых сервисов. **[доп.]** | Конкретизирует R1–R2 для проектирования репликации MS SQL и Kafka между ЦОД. |
| P   | **Производительность (Performance)** | |
| P1  | Время отклика операций в интернет-банке и на сайте — миллисекунды: p95 ≤ 300 мс для чтения (список депозитов, ставки, справочники), p95 ≤ 1 с для подачи заявки. | Требование бизнеса «отклик за миллисекунды» переведено в измеримые значения. |
| P2  | Справочные данные (продукты, ставки, справочники платежей) загружаются не дольше 300 мс — за счёт кэширования на стороне новых сервисов, без запросов в АБС. | Сейчас справочники при платежах загружаются больше секунды. |
| P3  | Новые сервисы масштабируются горизонтально; запросы равномерно распределяются между серверами, экземплярами приложений и ЦОД через балансировщик. | Требование бизнеса. Сервисы stateless, состояние — в БД/кэше. |
| P4  | Нагрузка от онлайн-каналов на АБС ограничена и управляема: АБС забирает заявки из очереди в своём темпе (back-pressure). **[доп.]** | АБС масштабируется только вертикально. |
| P5  | Система выдерживает пиковую нагрузку маркетинговых кампаний — не менее 10-кратного роста запросов к витрине ставок и заявок относительно среднего. **[доп.]** | Банк планирует кампании для привлечения клиентов; точное значение уточняется с бизнесом. |
| S   | **Поддерживаемость (Supportability)** | |
| S1  | Разрабатывается документация для дальнейшего расширения: OpenAPI-спецификации REST API, AsyncAPI-описание топиков Kafka, ADR, C4-диаграммы. | Требование: «предусмотреть документацию для дальнейшего расширения». |
| S2  | Депозитный функционал интернет-банка выносится в отдельные микросервисы с независимым релизным циклом, без изменения ядра платформы подрядчика. | Обновление ядра ИБ привязано к подрядчику; микросервисы — задел для будущих продуктов (кредиты, накопительные счета). |
| S3  | Архитектура расширяема на следующий этап — заявки на кредиты на сайте и в интернет-банке — без переработки интеграции. **[доп.]** | Кредитование — следующий приоритет бизнеса. |
| S4  | Централизованное логирование, метрики, трассировка запросов и алерты для новых сервисов и интеграций. **[доп.]** | Без мониторинга невозможно подтвердить 99,9 % и быстро найти «застрявшие» заявки. |
| S5  | Конфигурация продуктов и параметров депозитов (сроки, минимальные суммы) меняется без релиза. **[доп.]** | Ускоряет вывод новых продуктов. |
| +R  | **+ Ограничения (Restrictions)** | |
| +R1 | Данные, передаваемые с сайта и в интернет-банке, защищаются шифрованием трафика: TLS 1.2+ (HTTPS) для внешних каналов, TLS/mTLS между внутренними сервисами и в Kafka. | Передаются персональные данные и банковская тайна. |
| +R2 | Используются технологии, уже имеющиеся в банке: MS SQL и Oracle; .NET, Java, PL/SQL, React. Новые технологии должны быть совместимы с текущими платформами разработки, по ним должна быть экспертиза внутри банка. | Требование IT. Новые сервисы — ASP.NET Core (.NET) + MS SQL; адаптеры к АБС и системе КЦ — Java. |
| +R3 | Брокер сообщений — Apache Kafka. Текущая платформа интернет-банка (.NET Framework 4.5) несовместима с Kafka, поэтому с Kafka работают только новые сервисы на современном .NET. | Ограничение платформы ИБ. |
| +R4 | Нельзя дорабатывать функционал СМС в ядре интернет-банка (требует подрядчика) — СМС отправляются через отдельный сервис и существующий СМС-шлюз. | Требование IT. |
| +R5 | Сотрудники бэк-офиса депозитов и бэк-офиса кредитов не имеют доступа к данным друг друга: ролевая модель доступа в модуле ставок АБС. | Требования безопасности банка. |
| +R6 | Новые клиенты открывают депозит только после очной идентификации в отделении. | Регуляторное требование. |
| +R7 | Обработка персональных данных и банковской тайны соответствует законодательству РК и требованиям регулятора (АРРФР): хранение ПДн на территории РК, журналирование доступа. **[доп.]** | Банк работает в Казахстане. |
| +R8 | Сроки: MVP (заявка на депозит онлайн, обработка бэк-офисом) — 6 месяцев; полностью автоматическое открытие — 12 месяцев. | Цели бизнеса. |
| +R9 | Ресурсы ограничены текущими командами: ИБ — 10 + 10 человек у подрядчика, АБС — 20 человек (из них несколько с Java-экспертизой), подрядчик системы КЦ — 5 человек. **[доп.]** | Влияет на выбор: минимум новых технологий, последовательность работ в RoadMap. |
